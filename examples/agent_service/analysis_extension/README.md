# Analysis extension v1

Single-host extension for the existing AgentScope example service. It captures registered source adapters' ToolResponse objects before outer offload/context handling, then exposes AnalysisBuild, AnalysisInspect and AnalysisPublish through one middleware. Budget MCP v2 is a first-class built-in adapter. Exact values are decimal strings. Scenario choices belong to prompts: findingPlan, actionPlan and viewPlan explicitly select checks, advice and presentation. The host does not infer a negative-value investigation or fixed business workflow. The extension includes bounded model semantic review, optional host-managed headless rendering, and a managed Python environment. Playwright MCP selection is independent of internal rendering. It performs no budget write operations.

## Integration

`main.longterm_memory_factory` preserves AgenticMemoryMiddleware and appends `create_analysis_middlewares(...)`. AgentScope provides capabilities independently of Skill names: `capabilities.analysis` enables analysis follow-up, `capabilities.reports` enables AnalysisRenderReport, and either enables shared capture/read/build/publish tools and cards. Both default to true. `activation: disabled` stops all extension capabilities. Skills guide when and how to use tools; no selection, renaming, or removal of a Skill changes the capability policy. Ordinary queries still do not imply a request for analysis or reports.

The factory verifies selected Skill package hashes and records versions by resource ID. Existing ownership, session overrides and version pins remain enforced. MCP capture requires actual leased, enabled, user-owned tool bindings. Budget v2 recognition retains its schema and exact contract metadata checks; its request, pagination, continuation and evidence semantics live in the budget adapter. Other MCP tools continue to load and execute normally. To include their outputs in analysis, register a source adapter; this does not make arbitrary output automatically analyzable. Source-specific `numberFormats` and business rules remain explicit.

Supported config fields are `schemaVersion`, `activation`, `capabilities`, `sources`, `numberFormats`, `rules`, `findingRules` and `limits`. HTTP delivery and runtime tools share host policy and selected-package integrity checks. `sources` binds actual resource IDs and original tool names to adapters, rather than granting access to a resource. The adapter ID, version and options are required and frozen with each capture; changing current config never reinterprets a saved response. Inputs lacking this registration must be queried again; neither the response body nor the request contract is used to guess an adapter. Built-in budget recognition for live tools takes precedence over generic bindings.

For an existing JSON row tool, the built-in `json-records` adapter can be configured without changing that MCP:

```json
{"resourceId":"<actual resource ID>","toolName":"list_sales","adapter":"json-records","options":{"rowsPointer":"/records","idField":"id","labelField":"name","values":{"SALES":"amount"},"unitField":"unit","completePointer":"/complete","memberDimension":"recordId"}}
```

Place this binding in `sources`. `values` maps metric names to actual row fields; selectors always point to captured locations, never replacement numbers. Optional `periodField`, `dimensions` and `contextPointer` map actual metadata. Row IDs must be unique strings. Only a true `completePointer` value proves enumeration complete. Missing units stay empty and block calculations requiring units. No evidence verification or query continuation is invented for a generic JSON source. Implement a `SourceAdapter` for richer source-specific semantics and register it in `adapters.default_sources`.

Use `numberFormats: {"<registered resource id>": "grouped-dot"}` only for a source whose raw numeric strings were confirmed to use grouped thousands and a decimal point. It is a source decoding rule, not a money unit or scale assumption. Do not invent units or register conversion rules merely to make calculations pass. RECONCILE can compare identically labelled source values, including all-empty unit/scale labels, under an explicit caller-selected sum expectation; it does not invent units or register a source business rule.

Private files are under `examples/agent_service/analysis-data/`, outside model workspaces. Local config and data are gitignored. The SQLite registry commits only after an atomic, hashed content file write. Published versions cannot be overwritten. The host allocates revisions from analysisRef; model calls use requestKey and never supply expectedBaseRevision. Compare-and-swap remains inside the storage transaction. Each host operation rechecks agent/session access and owner identity. Existing budget permissionStatus is retained; this does not add source business authorization or an OS sandbox against arbitrary host code execution.

## Contract and limits

`artifact-v1.schema.json` freezes storage v1; `artifact-v1.example.json` is synthetic. Unknown noncritical fields may be added; unknown schema versions/operations never pass automatically. The current contract requires `findings`/`actions` (empty arrays when no plans select them), explicit presentation policy, finding version and source origins and independently stored action runs; see [ACTIONS_V1.md](ACTIONS_V1.md). Batch 2 adds registered chat cards and self-contained HTML through `AnalysisRenderReport`. See [PRESENTATION_V1.md](PRESENTATION_V1.md) for the frozen public projection and routing contract. The bounded renderer executes the explicit viewPlan; complete paginated details remain available without unrequested metrics or charts.

Defaults: 16 MiB per serialized capture/artifact, 512 MiB total content, seven-day retention for unpinned captures/orphans, 50,000 facts, 1,000 selections, 100 operators, 100 items per read page. Historical maximum tool output measured 747,790 UTF-8 bytes; a separate test exercises a response above 1 MiB. Limits apply jointly. Quota failures never save truncated data. Maintenance is throttled and runs off the event loop when due; pinned analysis sources and versions are retained. Back up SQLite and blobs together with the service stopped or a consistent SQLite backup procedure.

Resume-only requests are linked to captured parent executions using original resource, connection, tool, context, query session, resumeRef and server continuationOf. Include the whole captured chain in AnalysisBuild. Missing roots, gaps, unknown totals or unproven population enumeration do not become COMPLETE. Within one source/query context, conflicting observations remain conflicts. Across queries, facts retain distinct sourceContextId values even if execution, observation or evidence IDs repeat; verification and formula dependencies cannot cross those boundaries.

The default `scope.contextMode=SINGLE_SNAPSHOT` accepts reopened budget contexts and multiple query sessions on the same real connection and data boundary (`sourceId`, `snapshotId`, `asOf`, `schemaHash` and every other context field except `contextId`). Query identities, continuation cursors, execution/observation IDs and evidence remain bound to their original full context and session. Explicit `COMPOSITE` allows report composition across contexts or adapters. Facts retain their own contexts. Table columns group the same business metric across members by data boundary, period, binding, non-member dimensions, source, unit and scale; different query identities alone do not create duplicate columns. Repeated observations of the same member and metric remain separate facts and cannot silently overwrite one table cell: choose the intended observation or present explicitly labelled separate views. Distinct data boundaries remain distinct columns. Compilation into one report does not assert comparability. Inventory/capture discovery with `memberDimension` exposes `memberRef` and the original `sourceObjectId`. Use member refs when IDs collide across sources. The host normalizes cross-source analysis `objectId` and scope members to these references for tables, counts, filters, missing values and relations; original source dimensions remain unchanged. Use returned analysis IDs for selectors, and original IDs for MCP requests. A population enumeration proves only its own source’s subject members, never the complete population of other sources. Select actual fact references or `select.sourceContextId`/`period` for computations, and use meaningful topic/column labels in reports.

Business comparisons default to one period/binding/data boundary/origin and matching non-member dimensions. A configuration-maintained rule with `source`, `version` and `operators` can define `comparability`: explicit `periods`, `metrics` (bindingRef/measureCode/cellKey), `varyingDimensions`, `contexts` and `sourceOrigins`. An operation must opt in via `comparabilityRef`; each supplied bound applies to all inputs. Cross-boundary exceptions require the corresponding lists, while unit/scale and completeness checks still apply. SUM/LINEAR/CONVERT additionally require their existing arithmetic/business rules. Rule provenance is recorded on derived values. Ranked charts and filtered aggregate metrics reuse the original operation’s comparability rule from the saved rule registry. ARITHMETIC remains bounded pure arithmetic and does not grant business comparability or causation.

## Validation and activation

Native analysis results expose a single scalar-reference contract: ARITHMETIC `inputRefs` and COMPUTATION `workRefs.refs` accept either real IDs or `{valueRef, field?, nodeRef?}`. Expression variables remain positional `v0`, `v1`, etc.; they never contain copied source amounts. Field selection uses the same semantics as report bindings, including local versus recursive formula differences and DESCRIBE subset membership. Ordinary work methods may be explicitly corrected through `workRefs.operator`; FORMULA_CHECK, RECONCILE, SUM, LINEAR and CONVERT keep their source checks and business-rule requirements.

Build responses include `resultChanges` and `calculationSummary`. Unchanged successes return short reusable references; optional table/formula previews share a 12,000-character budget. Amounts, counts, formula status/differences and blocking diagnostics remain visible. `detailRead` retrieves the full frozen result; omitted previews are not missing source data. Full stored artifacts, dependencies and report datasets are unchanged. Exact repeated parameter failures are memoized only for the same frozen inputs, rules and preceding calculations in the current turn, and are separately counted in tool timing logs. The native capability version participates in Build idempotency.

Select source, analysis and report Skills for the desired guidance on an agent with the intended MCP resources. The host config controls available tools independently. `AnalysisInspect(section="protocol")` exposes deliveryCapabilities, sourceAdapters, contextModes and registered rules. Config and bindings are checked for each new runtime and HTTP request; an in-flight reply retains its runtime settings. Web UI delivery and the current local filesystem backend retain their existing behavior.

The report Skill owns presentation guidance and the existing visual reference; the analysis Skill owns calculations, interpretation and analysis review. Both reuse the existing structured result protocol and renderer. Skill separation does not modify the approved report HTML, CSS, chart components or schema version, and report requests do not imply permission to start analysis.

Only the current analysis, finding and presentation formats are accepted. There is no migration, missing-field repair, renderer upgrade-on-read or historical read-only path. Start a new analysis for acceptance. Current-protocol linked revisions, idempotent requests, restart recovery and immutable source evidence remain supported. Private storage must remain outside the model workspace.

Frontend checks, from `examples/web_ui/frontend`: `npm run test:analysis`, `npm run test:reports`, `npm run build`; lint the changed TypeScript/TSX files. No Java or Docker change is required by Batch 2.

The October 10 acceptance uses real read-only budget MCP calls and the actual SDK acting/middleware chain, with a local model stub that cannot call a network API. The user explicitly excluded external model calls. Skill package mounting and protocol checks passed; model-driven skill selection/wording remains untested and must not be reported as passed.

## Synthesis capabilities (engine 2.0.0)

AnalysisInspect(inventory) discovers all current-owner/session captures without new queries. It returns source/context/task/period, exact values, actual formula metadata, names and observation identity, with exact filters and pagination. Names are joined only within the same source and context; conflicting observations remain separate. Enumeration is bounded and fails explicitly at the configured capture/cell limits.

Every derived result separates executionStatus from numeric agreement. Formula nodes expose localCheck over captured direct inputs, recursive recalculation, propagatedDifference and differenceOriginRefs. Captured cross-table input values are included while their external formulas remain unexpanded; this is not missing expense. Blocked dependencies remain blocked.

RECONCILE explicitly requires aggregation=SUM, a captured direct relation, parent-first references and all direct children of the same metric/context. It returns parent minus the exact child sum. Confirmed leaves return NOT_APPLICABLE with no child sum or difference. The Skill currently selects parent-equals-children as the user's budget default; no backend scenario default or invented registered rule is added.

The renderer consumes model-selected labels, numberFormat/format and hierarchy comparisonRef. Number formatting never changes stored values or calculations. report.py, report.css and the approved reference HTML remain unchanged. No ontology service changes or historical migration are needed.


## Batched analysis work

Data receipts can include `analysisMaterials`: source values, formulas, context, exact selections and existing grid-file references within the original model-response budget. Full source receipts remain immutable. Models choose the question's scope; available selections do not imply that every available object belongs to it.

`QueryResultRead` and `AnalysisInspect` accept `requests` (up to 12 explicit, authorized reads) with optional `allPages`. Continuations retain filters and share a 24,000-character model projection. Partial reads return precise continuations; `readComplete` describes the requested saved fragment, not source-query completeness. Inspection batches allow only sections actually bound to their capture, analysis or Python-run reference. Large grids continue to use the existing file input instead of inline pagination.

`AnalysisPython.operations` uses existing native operators before the same Python execution, including formula checks against captured values. Default inputs include source facts and this call's operator outputs. Explicit input references may name a current operation ID. Small table/diagnostic payloads are returned inline with `payloadComplete`; large payloads retain read references. No report-template, business-aggregation, model-parameter or review-policy change is part of this feature.

## Analysis Python libraries

Native analysis is the first choice. `AnalysisBuild.operations` supports `DESCRIBE` for a same-metric source-value distribution (signed totals, counts including missing values, extrema, mean, ordered rows, shares and optional top N). This is a description of the selected source values, not a new consolidation or tree-deduplication rule. Budget-native aggregates and captured formulas remain authoritative. `documentInputs` exposes existing formula and descriptive datasets for direct report binding; formula datasets preserve raw nulls. Budget adapters declare BUDGET_NULL_ZERO_V1: captured null operands compute as zero and division by zero returns zero. Both waterfall paths consume the recorded effective inputs, retaining zero-length steps; unqueried, failed, conflicting or display-only inputs remain blocked. The approved template is unchanged.

The public `AnalysisPython` tool now requires `fallbackReason` alongside `purpose`: the missing capability and the processing performed. There is no new model approval or fixed scenario workflow. Each actual attempt stores a `capabilityDecision`, source code, input lineage, outputs, status and timing, including failures. Old internal calls are explicitly `UNDECLARED`; no historical reason is inferred. Administrators can export these records on demand using `scripts/export_analysis_capability_usage.py --data-dir <analysis-data> --agent-id <id> --session-id <id> [--include-code]`. Export reads the existing index; it adds no per-question directory scan.

`AnalysisPython` accepts normal `import` and `from ... import ...` from the host catalog. Standard calculation modules use the bounded local worker; pandas, NumPy, SciPy and statsmodels run only in a disposable Docker container. The server prepares a pinned image automatically and reuses it. Prewarm during deployment to keep package installation outside a user question:

```sh
PYTHONPATH=src:examples/agent_service python -m analysis_extension.python_environment
```

On Windows use the service Python and `PYTHONPATH=src;examples/agent_service`. The service identity needs access to Docker; this is independent from whether the CLI is installed. No fallback enables unrestricted host execution. `python-environment/requirements.lock` pins the complete dependency set with wheel hashes; the Dockerfile pins the base image digest. Catalog expansion is a server change, never a package name supplied by model code.

Each library execution has no network, a read-only root, no capabilities, no privilege escalation, the service UID/GID on Linux (to read owner-only captured grid files) or a non-root user on Windows, 1 GiB memory, two CPUs and one numerical-library thread. Only worker source and explicitly authorized grid files are mounted read-only. Input facts/files are passed as frozen JSON. Timeout or cancellation removes the container. The local standard worker remains at 256 MiB. This does not turn the entire AgentScope workspace into a container; it applies only to AnalysisPython.

Money stays Decimal with 128-digit context. pandas uses Decimal/object; normal sum/groupby calls default to min_count=1/dropna=False. Exported missing values are null and Decimal values use plain notation. Finite binary-float outputs are rejected rather than labeled exact; scientific estimation with float output is outside this release. Existing product structures remain SCALAR/TABLE/CHART_DATA/DIAGNOSTIC/FILE. Records include environmentId, imageId when applicable, libraries, prepareMs and executeMs. Exact requestKey retries preserve their original execution even after an environment upgrade.

API change: AnalysisBuild returns revision instead of baseRevision; AnalysisPublish no longer accepts expectedBaseRevision. Frozen preview repair and confirmPublish use only the returned references. Stored artifacts retain a private concurrency baseline, not another model-facing revision scheme. Old published snapshots remain immutable.

## Public stage narratives

ChatService observes public model/tool lifecycle events after completion middleware and publishes `CUSTOM` / `agent_progress` snapshots. Each snapshot has `version: 1`, a `replyId`, a monotonic `revision`, and bounded `steps`. The final snapshot is also stored in reply metadata as `agentProgress`, so event replay and history loading use the same text. Narratives remain separate from answer blocks. The UI renders plain paragraphs without stage headings or folding controls; every narrative remains visible during execution, after completion and on refresh. The overall status is informational. Existing raw tool details retain their separate disclosure.

Stages represent new public information, not every tool invocation. Known discovery receipts expose actual candidate names, supported grouping fields and scope values. Repeated receipts and bookkeeping calls do not create placeholder paragraphs; consecutive scope lookups are combined. The next paragraph is derived from an actually selected tool and its arguments, and stays absent until a next action is known. Stage titles remain internal metadata only. Candidate matches, request declarations, observed amounts and arithmetic results retain distinct meanings; a completed reply does not turn a failed operation into a successful one. Previously saved narrative text remains unchanged, while its presentation uses the current UI.

Running replies are checkpointed with their replay cursor at stage boundaries and at most every 128 events. History reads and checkpoint writes share a lock; cancellation completes the snapshot/cursor pair before mutating the reply again. The bounded replay tail remains available for a client connecting with a slightly older cursor, including when completion happens between its history read and SSE subscription. Batch-envelope placeholder rows are not counted as empty business results.

Capture records up to four observations before model projection or tool offloading. Tool providers can supply `metadata.public_progress = {version: 1, facts: [...]}`; every fact must include `text`, `sourceId`, and `state` (`observed`, `calculated`, or `verified`). Include `pointer`, `scope`, `value`, and `unit` for reproducible numeric observations. These are host-authored observations, never a container for model reasoning or arbitrary tool instructions. Returned row counts do not establish source completeness. Decimal strings retain their exact precision; monetary observations require an explicit unit. Missing group labels remain explicit.

Optional wording uses the configured model asynchronously, with one pending call, an eight-second timeout, and at most eight attempts per reply. The host substitutes exact facts into validated placeholders and permits only connective wording. Failure, timeout, or unsupported structured output keeps deterministic prose. Wording never delays tool execution, and only accompanies a real result or status update. Actual tool selection determines next actions; terminal replies reject late updates. Waiting, failure, interruption, and background results retain their own status.

Validation: run `python -m unittest discover -s tests -p service_reply_progress_test.py -v`, the capture/offload/chat-persistence suites, and `npm run test:agent-progress` plus `npm run build` in the frontend. `scripts/regress_reply_progress.py --capture-ref <existing-ref>` uses a saved real budget query with the configured live model and isolated SQL history. `--replay-events <result.json>` rechecks an already recorded real run entirely locally, without credentials or network calls. The live path uses the configured model provider; the local path does not make a fresh upstream business query. Open `/tests/progress-narrative.html` on the frontend development server to inspect the generated real-case fixture, history restoration, and light/dark layouts. Generated business data and screenshots stay in ignored `.cache` directories.

`scripts/regress_progress_narratives.py --messages <messages.json> --captures <captures.json> --output <directory>` reconstructs public events from the recorded five-group budget regression. It excludes thinking blocks and verifies distinct paragraphs, specific candidates/failures, the missing-group amount and an unchanged final answer. This is an offline quality regression and does not replace a fresh browser-to-provider-to-business-service test.


## Execution and instruction alignment

The application workspace uses `business_instructions.WORKSPACE_INSTRUCTIONS`; generic LocalWorkspaceManager users retain the default unless configured. Business agents can set `memory_config.memory_instructions` to the concise MEMORY_INSTRUCTIONS profile without disabling memory or changing other agents.

The system prompt owns intent, scope and acceptance principles; Skills own methods and boundaries; tool schemas own arguments; source receipts own current facts and recovery; code owns execution identity, precision and publication. Contract tests exercise the registered schemas and complete delivery paths, not only isolated methods.

Read-only query attempts are persisted in turn_progress. Unknown/in-progress results retain identity. Explicit FAILED/retryable/RETRY results receive a new identity up to max_query_retries (default 1); capture retains the failed evidence separately. Once exhausted, hostQueryRecovery reports QUERY_RETRY_LIMIT_REACHED without rewriting the captured source error. Partial continuation retains its source resume contract. Transport errors alone never authorize a new execution identity.

Budget FORMULA_CHECK applies its source-owned null/zero arithmetic policy in both local and recursive checks and preserves source null separately from effective values. Other sources without a declared null rule may complete with completionReason=SOURCE_VALUE_MISSING, calculationValidation=BLOCKED and null value. Completion counts the diagnosed check, numeric consumers still reject it. Actual missing references, conflicts and precision failures remain distinct. The artifact schema accepts only this constrained completed/blocked combination. Pure source rendering does not require an artificial workPlan; declared obligations survive rebuilds.

Data-preserving presentation revisions reuse facts and calculations through AnalysisPublish; changed data/scope/calculations use Build. Existing semantic review reuse follows its content/evidence fingerprint, while render checks remain snapshot-bound. A registered page is a complete report delivery; AnalysisRenderReport is only for an explicit export, and export failure does not invalidate the page.
# Query lineage and follow-up requests

The model-facing query accepts omitted unchanged `targets` and `sharedConditions`. The host restores them only from selected, connection-matched business receipts and retained intent evidence; a changed metric is never restored. Selecting one column of a multi-target receipt restores only that column's target. Explicit task/form names from the selected runtime context are valid evidence for reuse, not automatic defaults for independent queries.

`FACTS` filters or sorts frozen values. `MEMBERS` queries the selected members again, either with new conditions or with the original metric and a new `groupBy`; the budget service remains responsible for period validity and selected-ancestor removal. Repeated FACTS views preserve the original business request for subsequent context reuse, while their value filters remain query-local. A single empty target alias in a FACTS predicate is normalized only when the source identifies one metric unambiguously.

Task summaries retain candidate references and business conditions, while detailed historical receipts stay in the store. Report generation uses the existing `AnalysisBuild.documentDraft.path` and confirmed HTML template. Completed replies label earlier failed attempts as history without changing their error status or evidence.

Input identity includes immutable sources, selections, roles and member references. Rewording a goal, changing selection explanations or reordering the same adopted inputs does not invalidate formula preparation or saved calculations. Adoption and delivered-result freezing share this rule; restored conversations keep their existing version for unchanged inputs. Changing the actual source, selected members or roles still invalidates the previous input set.

Formula selection errors return bounded candidates from the selected metric and rows, together with the exact host read tool. Display names are not fact references. The host never selects a candidate automatically or replaces source nulls with inferred values.

Resuming a pending task traces only its explicitly selected base contexts to recognize replaced business wording. Its updated intent cannot revive an older metric through the still-selected member source. Native business result origins also bound answer candidates and source views for unfiltered queries: successful runtime probes that contributed no final facts are excluded, while final nulls and all returned metric columns remain available.
